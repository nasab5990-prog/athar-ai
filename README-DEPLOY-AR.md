# أثَر | دليل التشغيل والنشر الحالي

**النسخة:** PostgreSQL v3  
**الواجهة:** GitHub Pages — الفرع `main`  
**الخادم:** Render — الفرع `postgres-migration-test`  
**قاعدة البيانات:** PostgreSQL عبر Supabase/Render connection string

> هذا الدليل يحل محل تعليمات SQLite القديمة في الإصدارات السابقة. لا تستخدم رابط خدمة Render القديمة ولا تنقل إعدادات SQLite إلى الخدمة الحالية.

## 1. الروابط الحالية

- واجهة المنصة: https://nasab5990-prog.github.io/athar-ai/
- API: https://athar-ai-postgres-test.onrender.com
- فحص صحة API: https://athar-ai-postgres-test.onrender.com/api/health
- نمط الدخول: https://athar-ai-postgres-test.onrender.com/api/auth/mode

ملف `config.js` في الواجهة يشير إلى عنوان API الحالي. لا تغيّر العنوان إلا عند اعتماد خدمة بديلة وتحديث إعدادات CORS واختبار الاتصال.

## 2. بنية المستودع

- `main`: ملفات الواجهة المنشورة على GitHub Pages.
- `postgres-migration-test`: ملفات الخادم وقاعدة PostgreSQL.
- لا تنشر ملفات فرع الخادم فوق ملفات الواجهة، ولا تستبدل خدمة Render الحالية بالخدمة القديمة.
- احتفظ بملفات SQLite القديمة كنسخ مصدرية/احتياطية؛ تشغيل الخادم الحالي يعتمد PostgreSQL ولا يستخدم SQLite قاعدة تشغيل أساسية.

## 3. متطلبات تشغيل الخادم

من جذر مشروع الخادم:

```bash
npm install
npm start
```

يجب أن تكون قاعدة PostgreSQL متاحة قبل بدء الخادم. يستخدم الخادم `DATABASE_URL`، ويرفض بدء التشغيل إذا لم تكن القيمة موجودة.

## 4. متغيرات البيئة في Render

راجع المتغيرات التالية في خدمة الخادم، ولا تضع قيم الأسرار داخل GitHub أو ملفات الواجهة:

| المتغير | الغرض |
|---|---|
| `DATABASE_URL` | رابط اتصال PostgreSQL؛ سرّ لا يُشارك |
| `NODE_ENV` | استخدم `production` في الخدمة المنشورة |
| `SESSION_SECRET` | سر جلسات عشوائي قوي، 32 حرفًا على الأقل |
| `OTP_SECRET` | سر مختلف لتوليد/التحقق من رموز الدخول، 32 حرفًا على الأقل |
| `FRONTEND_ORIGIN` | `https://nasab5990-prog.github.io` دون مسار المشروع |
| `COOKIE_SAMESITE` | `none` عند استخدام الواجهة والخادم على نطاقين مختلفين عبر HTTPS |
| `DEMO_LOGIN_ENABLED` | `true` لوضع العرض التجريبي فقط، و`false` قبل الاستخدام الرسمي |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM` | إعداد البريد عند تفعيل الدخول برمز تحقق |

الخادم يضبط جلسات PostgreSQL عبر `connect-pg-simple`، ويستخدم Cookie آمنًا في وضع الإنتاج. لا تضع `DATABASE_URL` أو أسرار الجلسات في `config.js`.

## 5. وضع العرض التجريبي

عند تفعيل `DEMO_LOGIN_ENABLED=true` يعرض الخادم مسار دخول تجريبيًا. استخدم بيانات اصطناعية فقط، وتأكد من عزلها في مدرسة Demo. لا تستخدم أسماء أو أرقامًا أو نتائج طلبة حقيقيين في العرض العام.

هذا الوضع ليس نظام دخول رسميًا للمدارس. قبل الاستخدام الفعلي:
1. عطّل الدخول التجريبي.
2. جهّز SMTP واختبر وصول رمز التحقق.
3. أنشئ حساب مدير المدرسة من مسار إداري موثوق، ثم أنشئ حسابات المدرسة واربط الطالب بولي الأمر/الطالب بحسب الدور.
4. راجع سياسة الخصوصية والموافقات والصلاحيات المعتمدة لدى الجهة التعليمية.

الدخول الرسمي يقبل نطاقي البريد `@moe.om` و`@edu.moe.om` وفق تحقق الخادم.

## 6. تهيئة قاعدة البيانات والتحقق

- استخدم أدوات `db:setup` و`db:verify` فقط بعد مراجعة محتواها وإعداد نسخة احتياطية وخطة تهيئة مناسبة.
- لا تشغّل `test/postgres-smoke.js` على قاعدة البيانات الحية؛ قد ينشئ/يعدل/يحذف سجلات اختبار.
- لا تنفذ ترحيلًا أو حذفًا أو إعادة تهيئة على قاعدة Supabase المستخدمة دون نسخة احتياطية وموافقة صريحة.
- لا تفترض أن بيانات SQLite القديمة انتقلت تلقائيًا إلى PostgreSQL. الترحيل عملية منفصلة تتطلب مطابقة السجلات والتحقق من أعدادها وروابطها وصلاحياتها.
- فحص الصحة المتوقع يعيد JSON يتضمن `ok:true` و`database:"postgresql"`. هذا يثبت اتصال الخادم بقاعدة البيانات وقت الفحص، ولا يثبت وحده صحة جميع وظائف المنصة.

## 7. الفحوصات الآمنة

في فرع الخادم:

```bash
node --check server.js
node --check database.js
node --check db-setup.js
node --check db-verify.js
node --test test/postgres-scope-regression.test.js
```

هذه الاختبارات الثابتة تتحقق من أنماط الكود ونطاقات الصلاحيات؛ لا تعد بديلًا عن اختبار قبول متكامل على بيئة اختبار معزولة. لا تختبر الصلاحيات باستخدام بيانات طلبة حقيقية.

في فرع الواجهة، يستخدم Workflow الخاص بالمستودع فحوصات صياغة JavaScript وتدقيق الاعتماديات، ويُبنى الموقع وينشر عبر GitHub Pages.

## 8. ما يجب اختباره قبل الإطلاق الرسمي

- تسجيل الدخول والخروج وانتهاء الجلسة واستعادة الجلسة.
- الصلاحيات لكل دور: المعلم، المعلم الأول، المدير، المشرف، ولي الأمر، الطالب.
- عزل المدارس، وإسناد المعلم، وربط حساب الطالب وولي الأمر.
- إنشاء تقويم وتشغيل الرادار وحفظ التدخل وربطه بالتقويم الصحيح.
- حفظ قياس الأثر والتحقق من ربطه بالتدخل والطالب/الصف.
- تقارير المدير والمشرف، والطباعة، وتصدير/استيراد البيانات.
- العرض على أحجام الشاشات المختلفة، ومع اتصال ضعيف أو منقطع حيثما أمكن.
- اختبار استعادة النسخ الاحتياطية، وسياسة الاحتفاظ بالبيانات، وإجراءات معالجة الحوادث.

**حدود الإثبات:** نجاح فحوصات الصياغة والاعتماديات والاختبارات الثابتة لا يعني أن جميع الوظائف اجتازت اختبار متصفح أو اختبارًا ميدانيًا. يجب توثيق كل اختبار فعلي بنتيجته وتاريخه وبيئته.

## 9. حدود التحليل والمحتوى التعليمي

- نتائج الرادار والتوصيات أدوات مساندة مبنية على البيانات المتاحة، وليست تشخيصًا نهائيًا للطالب.
- على المعلم مراجعة المقترحات واعتماد التدخل أو تعديله.
- لا تنسب نواتج تعلم إلى درس بعينه إذا كان المصدر الرسمي يوثقها على مستوى الوحدة فقط.
- لا تصف التغطية بأنها شاملة لجميع الصفوف والمواد إلا بعد توثيق الوحدات والدروس ونواتج التعلم من مصادر وزارة التربية والتعليم.
- بيانات Demo لا تمثل عينة ميدانية، ولا يجوز استخدامها لإثبات تحسن تعلم حقيقي أو أثر سببي للتدخلات.

## 10. الاستعداد للمسابقة

يجب أن يتضمن ملف المشاركة:
1. وصف المشكلة التربوية والفئة المستفيدة.
2. أهداف المنصة وآلية العمل من التقويم إلى التدخل وقياس الأثر.
3. مصادر المحتوى والمنهج مع الصف/المادة/الوحدة/الدرس والطبعة أو السنة والصفحة عند توفرها.
4. مخطط البنية التقنية وتدفق البيانات والصلاحيات.
5. سياسة الخصوصية وحماية بيانات الطلبة وحدود استخدام الذكاء الاصطناعي.
6. نتائج اختبارات موثقة، مع فصل الاختبارات التقنية عن التجربة الميدانية.
7. أدلة استخدام فعلية مصرح بها بعد إخفاء الهوية، إن توفرت؛ وإلا يصرّح بأن الاختبار الميداني لم يكتمل.
8. فيديو شرح لا يتجاوز 3 دقائق، يوضح رحلة استخدام حقيقية دون كشف بيانات شخصية.
