# ATHAR PostgreSQL Migration — Preview Branch

This document records the migration scope for `migration/postgres-preview`.
The production `main` branch and Render service must remain unchanged until the
preview has passed the acceptance checks below.

## Current architecture discovered

- `server.js` uses `better-sqlite3` synchronously for users, OTP codes,
  audit events, records, student links, teacher assignments, and analysis.
- Sessions use `connect-sqlite3` and a local SQLite file.
- `create-user.js` and `seed-user.js` also open SQLite directly.
- The frontend calls the existing `/api/*` routes with cookie credentials;
  route paths and response shapes should remain compatible.
- Demo login is controlled by `DEMO_LOGIN_ENABLED=true`. It creates five
  isolated demo identities in `DEMO-SCHOOL` and must remain available in
  preview. It must not create learner records or scores.
- No SQLite backup was available when this migration began. Historical data
  must not be represented as migrated or recovered.

## Required PostgreSQL design

1. Use the Supabase Session Pooler connection string from `DATABASE_URL`.
2. Use `pg` with parameterized queries and PostgreSQL transactions.
3. Use a PostgreSQL-backed Express session store (not SQLite sessions).
4. Create schema migrations for:
   - `users`
   - `otp_codes`
   - `audit_log`
   - `records`
   - `account_students`
   - `teacher_students`
5. Preserve role checks, school scoping, ownership checks, and student-link
   permissions in every relevant route.
6. Replace SQLite JSON extraction with PostgreSQL JSONB expressions or
   equivalent parameterized predicates. Store record payloads as JSONB while
   preserving the API's object-shaped `payload`.
7. Update `create-user.js` and `seed-user.js` to use the same PostgreSQL
   connection and schema rules.
8. Keep OTP email behavior unchanged; demo login must work even when SMTP is
   not configured.

## Important compatibility details

- PostgreSQL IDs should use `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Store `records.payload` as `JSONB NOT NULL`; query student IDs with
  `payload->>'student_id'`.
- Store booleans as `BOOLEAN`, not SQLite integer flags.
- Use `TIMESTAMPTZ` for expiry/creation timestamps where appropriate.
- Use explicit transactions for bulk imports, user creation/link updates,
  student deletion, and demo fixture initialization.
- Avoid changing frontend route names, JSON keys, or Arabic error messages
  unless a verified compatibility issue requires it.

## Preview acceptance checks

- Server starts with `DATABASE_URL` and no `DB_PATH`.
- `GET /api/health` returns the existing health response.
- `GET /api/auth/mode` reports demo mode when enabled.
- Demo login succeeds for all five roles and creates no learner fixtures.
- Add one student individually and several students in bulk.
- Create assessment, intervention, impact, and analysis records.
- Confirm role-specific access and school isolation.
- Restart/redeploy the preview server and verify records and sessions behave
  as designed (sessions may expire; durable records must remain).
- Run `npm run check` and targeted API integration tests.
- Only after all checks pass should a pull request to `main` be considered.

## Deployment safety

Do not change Render environment variables, deploy this branch to the current
production service, delete SQLite files, or merge into `main` as part of
preparation. Configure a separate preview service only after the code is
ready and reviewed. Never commit `DATABASE_URL`, passwords, or other secrets.
